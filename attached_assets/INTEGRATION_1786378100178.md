# SAND — Preview Sandbox Integration Guide

Give this file to the agent building your app. It contains everything needed
to add live previews. No other document is required.

---

## What SAND does

You send project files. SAND runs them in an isolated container and returns a
public HTTPS URL that renders the app. The URL is iframe-safe.

```
POST files  →  SAND  →  https://<id>.prw.kodu.live  (live, hot-reloading)
```

Supported project types (`mode`):

| `mode` | Runs | Use for |
|---|---|---|
| `"app"` | Next.js 15 + React 19 + Tailwind v4 dev server | Web apps (default choice) |
| `"expo"` | Vite + react-native-web | Mobile-style apps |
| `"static"` | Static file server | Plain HTML/CSS/JS |

---

## Configuration

```
SAND_URL = https://prw.kodu.live
SAND_KEY = <bearer token>
```

Every `/api/*` request needs `Authorization: Bearer ${SAND_KEY}`.

**Server-side only.** Never expose `SAND_KEY` to the browser.

## Minimal working integration

```ts
const BASE = process.env.SAND_URL!;
const KEY = process.env.SAND_KEY!;

async function sand(method: string, path: string, body?: unknown) {
  const res = await fetch(BASE + path, {
    method,
    headers: {
      Authorization: `Bearer ${KEY}`,
      ...(body ? { "Content-Type": "application/json" } : {}),
    },
    body: body ? JSON.stringify(body) : undefined,
    // create can take up to 90s; give it 100s
    signal: AbortSignal.timeout(100_000),
  });
  return { status: res.status, data: res.ok ? await res.json() : null };
}

// 1. CREATE — returns only after the page actually serves HTTP 200
export async function createPreview(files: { path: string; content: string }[]) {
  const { status, data } = await sand("POST", "/api/previews", {
    files,
    mode: "app",
    ttlMin: 15,
  });
  if (status === 503) return { full: true };          // capacity — retry later
  if (status !== 200) throw new Error(`SAND ${status}`);
  return data; // { id, url, warm, ready, reason? }
}

// 2. UPDATE — hot reload, no new container, keeps the same URL
export async function updateFiles(id: string, files: { path: string; content: string }[]) {
  const { status } = await sand("PUT", `/api/previews/${id}/files`, { files });
  if (status === 404) return { gone: true };          // expired — create a new one
  return { ok: status === 200 };
}

// 3. KEEPALIVE — call every 5 minutes while the preview tab is visible
export async function keepAlive(id: string) {
  const { status } = await sand("POST", `/api/previews/${id}/keepalive`, {});
  return status === 200;                              // false → preview is gone
}

// 4. DELETE — when the user closes the project
export async function stopPreview(id: string) {
  await sand("DELETE", `/api/previews/${id}`);
}
```

## Status codes — the meaning is part of the contract

| Code | Meaning | What you must do |
|---|---|---|
| `200` | Success | — |
| `401` | Bad or missing key | Fix config. Retrying is pointless |
| `404` | **Preview expired or gone** | **Create a new one.** Not an error — previews are ephemeral |
| `429` | Rate limited | Wait, retry |
| `503` | **Capacity full** (`Retry-After` header) | Show "server busy, try again", or fall back to another provider |
| `500` | Internal error | Log it, show a generic message |

**Treating `404` as a hard error is the most common integration bug.** A preview
that has expired is normal; the correct response is to create a fresh one, not
to show the user an error.

## `ready` and `reason` — decide what to show the user

`POST /api/previews` waits until the page serves HTTP 200, then returns.
If it could not reach 200 within 90 seconds, you get `ready: false` plus a
`reason`. **The right action differs per reason:**

| `reason` | Cause | What to do |
|---|---|---|
| `compile_error` | The generated code has a build error | Fetch `GET /api/previews/:id/logs` and **show the error to the user**. Retrying elsewhere is pointless — the same code fails anywhere |
| `oom` | Container ran out of memory | **Infrastructure problem, not the user's code.** Retry, or fall back to another provider |
| `timeout` | Page never became ready in 90s | Same as `oom` — retry or fall back |

```ts
const p = await createPreview(files);
if (p.ready === false) {
  if (p.reason === "compile_error") {
    const logs = await sand("GET", `/api/previews/${p.id}/logs?tail=100`);
    showBuildErrorToUser(logs.data.stdout + logs.data.stderr);
  } else {
    retryOrFallback();  // our problem, not the user's
  }
}
```

## Lifetime rules

- A preview dies after **15 minutes of inactivity**. `keepAlive` resets the clock.
- Call `keepAlive` **every 5 minutes while the tab is visible**, and immediately
  on `visibilitychange` when the tab becomes visible again.
- **Do not** keep beating while the tab is hidden — that holds a slot the whole
  time. Bind the heartbeat to `document.visibilityState === "visible"`.
- `updateFiles` also resets the clock, so active editing keeps it alive.
- Maximum lifetime is 8 hours regardless of keepalive.

```ts
let timer: ReturnType<typeof setInterval> | undefined;

function startHeartbeat(id: string) {
  const beat = () => { if (document.visibilityState === "visible") keepAlive(id); };
  beat();
  timer = setInterval(beat, 5 * 60 * 1000);
  document.addEventListener("visibilitychange", beat); // instant beat on return
}
```

## Timing — what users experience

Measured on the production server (16GB, 6 vCPU):

| | `app` (Next.js) | `expo` (Vite) |
|---|---|---|
| Create, warm pool hit | **~5-7s** | — |
| Create, cold start | ~30s | **~3s** |
| `updateFiles` → visible change | **~1s** | ~0.3s |

A warm pool of 2 containers stays pre-booted, so most creates are warm.
`updateFiles` is the number that matters most — it is what the user feels on
every edit.

**Always show a progress indicator on create.** Even the warm path is several
seconds, and a cold start is 30.

## Sending files

```ts
files: [
  { path: "app/layout.tsx", content: "..." },
  { path: "app/page.tsx",   content: "..." },
  { path: "app/globals.css", content: '@import "tailwindcss";' },
  { path: "components/Card.tsx", content: "..." },
]
```

Rules:

- Paths are **relative to the project root**, no leading `/`
- `mode: "app"` — you **must** send `app/layout.tsx`; the template ships an
  empty `app/` directory and no page/layout of its own
- Tailwind v4 is preinstalled. Use `@import "tailwindcss";` (not the v3
  `@tailwind` directives)
- Available out of the box: `next@15`, `react@19`, `tailwindcss@4`,
  `typescript`. **Anything else is not installed** — the container has no
  internet access, so `npm install` will not work
- Total payload limit: 5MB

## Other endpoints

```
GET  /api/previews/:id/logs?tail=200   → { stdout, stderr, truncated }
POST /api/previews/:id/exec            → { exitCode, stdout, stderr, timedOut }
POST /api/previews/:id/read            → { files: [{ path, content?, error? }] }
GET  /api/previews                     → list of live previews
GET  /__health                         → status + counters (no auth needed)
```

`exec` runs a shell command inside the container as the `node` user (60s
default timeout, 300s max). Useful for `./node_modules/.bin/tsc --noEmit`.
A non-zero `exitCode` is **not** an API error — the call returns 200 and you
check `exitCode` yourself.

`read` accepts absolute paths (`/tmp/next-dev.log`) as well as project-relative
ones.

## Capacity

- **5 concurrent previews** on the current server
- A warm pool of 2 keeps starts fast
- When full, create returns `503` with `Retry-After: 30`

`GET /__health` returns live counters — no auth required, no rate limit, safe
to poll every 10-30s from an admin dashboard:

```json
{
  "previews": 2, "maxPreviews": 5, "warmPool": 2,
  "counters": {
    "created": 41, "warm": 38, "cold": 3, "capacityFull": 0,
    "warmMsLast": 5210, "warmMsMax": 8900, "warmSlow": 0,
    "coldMsLast": 29400, "coldMsMax": 31200, "createSlow": 0,
    "oomKilled": 0, "expired": 12, "expiredUnused": 4,
    "longLived": 1, "maxLifetimeMs": 4210000
  }
}
```

What the counters tell you:

| Rising counter | Meaning | Fix |
|---|---|---|
| `capacityFull` | 5 slots is not enough | Bigger server |
| `cold` | Warm pool too small | Raise pool size |
| `oomKilled` | Container memory too low | Raise memory limit |
| `warmSlow` (with `oomKilled: 0`) | Compiles are getting slow | Investigate the project size |
| `expiredUnused` | Users abandon tabs | Shorten TTL |

## Integration checklist

- [ ] `SAND_URL` / `SAND_KEY` in server-side env only
- [ ] Create timeout set to **100s** (SAND's internal wait is 90s)
- [ ] `404` triggers "create a new preview", not an error screen
- [ ] `503` shows "busy, retry" or falls back
- [ ] `ready: false` branches on `reason` (`compile_error` vs `oom`/`timeout`)
- [ ] Heartbeat every 5 min, bound to tab visibility
- [ ] `stopPreview` on project close
- [ ] Progress indicator during create
- [ ] `app/layout.tsx` included in every `mode: "app"` payload
